## 2단계 — 모집 설정·공개 상태

- [x] 회장단 관리 성공과 일반 ADMIN/USER의 관리 거절 경로를 구현했다. (기존 `requirePresidentTeam` 재사용)
- [x] 시작 직전·시작·종료 직전·종료·조기 마감·취소·일정 미설정을 단위 테스트로 검증했다.
- [x] 공개 API에서 초안·일정 미설정 회차와 관리 전용 필드가 노출되지 않는다.
- [x] migration 및 기존 기능 영향 검증 — `FlywayMigrationSchemaTest` 통과.
- [ ] 프론트 인계 — 문서 작성 완료, **서버 기동 후 실제 호출 확인이 남았다**.

| 구분        | 파일                                                                          |
| ----------- | ----------------------------------------------------------------------------- |
| migration   | `db/migration/V5__add_staff_recruitment.sql` (테이블 3개 신규)                 |
| domain      | `domain/staffrecruitment/StaffRecruitment` 외 부서·문항 엔티티와 상태 enum 3종 |
| application | `StaffRecruitmentService` + command·조회 DTO                                   |
| web         | 공개 컨트롤러, 회장단 컨트롤러, 요청·응답 DTO                                  |

설계 결정

- 접수 가능 여부와 접수 상태는 저장하지 않고 `StaffRecruitment`에서만 계산한다.
- 동시 게시는 애플리케이션 검사와 `published_slot` 유니크 제약으로 이중 방어한다.
- 부서·문항은 보낸 목록으로 전체 교체한다. 제출이 쌓이면 계약 재검토가 필요하다.
- 응답 시각만 `OffsetDateTime`으로 변환한다. 기존 API 직렬화는 바꾸지 않았다.

## 3단계 — 지원서 제출·본인 내역·회장단 조회

- [x] 정상 제출·본인 조회·회장단 조회 경로를 구현했다.
- [x] 타인 지원서·다른 회차 문항·접수 기간 외·중복 제출 실패 조건을 단위 테스트로 검증했다.
- [x] 채택 범위(즉시 제출만)에 맞춰 상태와 endpoint를 늘리지 않았다.
- [x] 기존 회원·스터디 지원 API의 계약을 변경하지 않았다.
- [ ] 프론트 인계 — 문서 작성 완료, **서버 기동 후 실제 호출 확인이 남았다**.

| 구분        | 파일                                                                                   |
| ----------- | -------------------------------------------------------------------------------------- |
| migration   | `db/migration/V6__add_staff_application.sql` (테이블 3개 신규)                          |
| domain      | `StaffApplication`, `StaffApplicationChoice`, `StaffApplicationAnswer`, 상태 enum        |
| application | `StaffApplicationService` + 제출 커맨드·상세·목록 DTO                                   |
| web         | `StaffApplicationController`(지원자), `AdminStaffApplicationController`(회장단)          |
| 공통 수정   | `ErrorCode` FOR153~157                                                                   |

설계 결정

- 지원 자격은 현재 활동 학기의 `tb_study_user` 존재로 판정한다. 회비 플래그로 판정하지 않는다.
- 제출 시점의 이름·이메일·전화·학과를 지원서에 복사해 영구 보관한다. 회원 FK는 `ON DELETE SET NULL`이다.
- 중복 제출은 사전 조회와 `(recruitment_id, applicant_user_id)` 유니크 제약으로 이중 방어한다.
- 목록 정렬은 `application_id DESC` 고정이며 계약의 `sort` 파라미터는 아직 지원하지 않는다.
- 임시저장·수정·취소·재지원·첨부는 채택되지 않아 구현하지 않았다. 상태는 `SUBMITTED` 하나다.

## 4단계 — 회차별 지원서 열람 권한

- [x] 회장단·미초대 ADMIN·초대자·다른 회차·회수·만료 조합을 단위 테스트로 검증했다.
- [x] 지원서 목록과 상세가 같은 권한 조건을 쓴다.
- [x] 접수 마감 후에도 권한이 유효하면 열람할 수 있다. (마감과 만료를 분리)
- [x] 초대가 다른 관리 기능의 권한을 추가하지 않는다. 전역 role과 JWT는 그대로다.
- [ ] 프론트 인계 — 문서 작성 완료, **서버 기동 후 실제 호출 확인이 남았다**.

| 구분 | 파일 |
| --- | --- |
| migration | V7__add_staff_recruitment_reviewer.sql (테이블 1개 신규) |
| domain | StaffRecruitmentReviewer, StaffReviewerStatus |
| application | StaffReviewerService + 후보·열람자 DTO |
| web | AdminStaffReviewerController, 지원서 컨트롤러의 권한 검사 교체, reviewable 조회 추가 |
| 공통 수정 | ErrorCode FOR158~160 |

설계 결정

- 권한 상태는 저장하지 않고 회수·만료 시각으로 계산한다. 지원서 요청마다 다시 확인하므로 회수 직후 바로 막힌다.
- 후보 목록은 회차 학기 운영진 전원이며 ADMIN 계정 보유 여부를 플래그로 준다. 부여는 ADMIN만 허용한다.
- 같은 회차 지원자에게는 부여할 수 없고 부여 후 지원하면 열람이 막힌다. 회장단은 차단하지 않았다(정책 확정 필요).
- 재부여는 기존 행을 되살려 이력 행이 중복되지 않는다.

## 5단계 — 명예의 전당 콘텐츠 관리·게시

- [x] 관리자 등록·미리보기·게시·중단과 공개 조회를 구현했다.
- [x] 초안과 게시 중단 항목의 공개 직접 조회가 차단된다.
- [x] 시즌 필터로 과거 기록을 계속 조회할 수 있다.
- [x] 기존 작품·해커톤·회원 응답 계약을 유지했다.
- [ ] 프론트 인계 — 문서 작성 완료, **화면 구현과 실제 연동이 6단계로 남았다**.

| 구분 | 파일 |
| --- | --- |
| migration | V8__add_hall_of_fame.sql (전시 항목·배지·성취 3개 테이블) |
| domain | HallOfFameEntry, HallOfFameAchievement, HallOfFameStatus |
| application | HallOfFameService + 입력 커맨드·조회 DTO |
| web | HallOfFameController(공개), AdminHallOfFameController(회장단) |
| 공통 수정 | ErrorCode FOR161~163, SecurityConfig 공개 GET 경로 2개 |

설계 결정

- 공개 조회는 게시 상태만 반환한다. 미리보기는 별도 경로 없이 회장단 인증이 필요한 관리 상세를 쓴다.
- 전시 인물은 회원 연결이 선택이며 이름을 값으로 복사한다. 탈퇴 시 FK만 끊고 게시된 소개는 남긴다.
- 이미지·배지·성취는 보낸 값으로 교체한다. 이미지 교체 시 이전 파일은 커밋 후 정리한다.
- 공개 목록은 offset 페이지네이션만 지원한다. display_order 정렬이라 커서 키가 단조롭지 않다.
- 배지는 JSON 컬럼 대신 자식 테이블에 저장한다. API 모양은 문자열 배열 그대로다.

## 검증 결과

| 검증                                      | 2단계                       | 3단계                        |
| ----------------------------------------- | --------------------------- | ---------------------------- |
| `./gradlew.bat build`                     | 통과 (343개, 실패 0)        | 3단계 355개 / 4단계 371개, 실패 0 |

| 단위 테스트                               | 18개 (도메인 11, 서비스 7)  | 12개 (서비스)                |
| 엔티티 ↔ migration 컬럼 대조 (수동 스크립트) | 불일치 없음                 | 불일치 없음                  |

Testcontainers 기반 테스트에는 Docker Desktop이 필요하다. 첫 기동에 `docker-desktop` WSL 배포판 초기화가 필요해 시간이 걸리고, 권한 서비스(`com.docker.service`)는 관리자 권한이 있어야 시작된다.

### 남은 검증 (2·3단계 공통)

1. 로컬 MySQL + `local` 프로파일로 서버 기동 — `ddl-auto: validate` 확인과 실제 요청 호출. 이 PC에는 로컬 MySQL이 없고 설정이 `127.0.0.1:3307`을 바라보므로 Docker로 DB를 띄워야 한다.
2. 회장/부회장 ADMIN 계정으로 생성 → 게시 → 공개 조회 → 지원서 제출 → 회장단 열람 → 마감까지 수동 확인.
3. 일반 ADMIN·비로그인·비활동부원 요청의 403·401 확인.
4. frontend 어드민 화면 → 홈 배너 → `/club/recruit` 반영 확인 (한지석과 공동).

## 다음 단계 선행 조건

4단계(회차별 열람 권한)는 초대 대상·수락 방식·만료 정책이 정해져야 한다. 계약 r2의 제안은 기존 ADMIN 계정과 회차 학기 운영진의 교집합에 즉시 부여하고 즉시 회수하는 방식이다.
