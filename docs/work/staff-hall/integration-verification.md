운영 비밀이 섞이지 않도록 아래를 셸에서 명시적으로 덮어썼다. `bootRun`은 저장소 `.env`를

| 항목                        | 값                                      | 이유                                              |
| --------------------------- | --------------------------------------- | ------------------------------------------------- |
| `RDS_URL`                   | `jdbc:mysql://127.0.0.1:3308`           | 기존 로컬 DB(3307)를 건드리지 않는 전용 컨테이너  |

## 발견한 결함과 수정

### 1. 명예의 전당 게시·게시 중단 응답의 `version`이 1 뒤처진다 (심각)

`publish`·`unpublish`가 flush 전에 응답 DTO를 만들어, DB는 `version=1`인데 응답은 `0`을
돌려줬다. 화면이 그 값으로 다음 요청을 보내면 무조건 `FOR145-409`가 난다. 실제로
게시 직후 게시 중단이 불가능했고, 이미 게시된 항목의 재게시도 `FOR163` 대신 `FOR145`가 났다.

같은 이유로 이미지 업로드 응답에도 올라간 `version`이 없어, 업로드 뒤 수정·게시가 409가 됐다.

- 수정: `publish`·`unpublish`·`uploadImage`에서 `detail()` 전에 `flush()`.
- 수정: 이미지 업로드 응답에 `version` 추가 (`{image_url, version}`).
- 재검증: 생성 0 → 게시 1 → 중단 2 → 재게시 3이 응답 값만으로 이어지고 DB와 일치한다.

### 2. 모집 수정 시 부서 이름을 유지하면 항상 409다 (심각)

부서·문항을 `clear()` 후 재삽입해서, Hibernate가 orphan 삭제보다 INSERT를 먼저 보내
`uk_staff_recruitment_department_name`을 위반했다. **지원서가 0건인 초안에서도 재현된다.**
부서 이름을 하나라도 유지한 수정은 전부 실패하므로, 실사용에서 모집 수정이 거의 항상 깨진다.

### 3. 지원서가 제출되면 모집 수정이 영구 불가다 (심각)

전체 재삽입이 제출된 지원서가 참조하는 부서를 지우려 해 FK 제약(1451)에 걸렸다.
계약 "모집·부서·문항은 제출이 생긴 뒤 물리 삭제하지 않는다"와 어긋났고, 오류도 뜻이 통하지
않는 `FOR145`로 나갔다.

2·3번 수정: 전체 교체를 **식별자 기준 병합**으로 바꿨다.

| 입력                       | 동작                                                      |
| -------------------------- | --------------------------------------------------------- |
| `department_id`·`question_id` 있음 | 그 행을 수정한다. 식별자가 유지돼 지원서 참조가 끊기지 않는다 |
| 식별자 없음                | 새로 추가한다                                             |
| 보낸 목록에서 빠짐         | 지운다. 단 제출된 지원서가 있으면 `FOR164-409`로 거절한다 |

제출 후에도 제목·요약·기간 수정, 부서 내용 수정, `active: false` 숨김, 부서 추가는 된다.
더 뽑지 않는 부서는 지우는 대신 숨긴다.

- 재검증: 이름 유지 수정이 통과하고 부서 id가 그대로다(7 → 7). 제출 후 삭제는 `FOR164-409`,
  숨김·추가·제목 수정은 성공, 기존 지원서의 부서 참조도 그대로다.

### 4. 깨진 요청 본문이 400이 아니라 500이다 (중간)

`HttpMessageNotReadableException` 핸들러가 없어 마지막 `Exception` 핸들러로 떨어졌다.
보낸 쪽 잘못인데 서버 오류로 보고된다. 신규 기능이 아니라 전역 핸들러의 빈틈이며 모든 API에
해당한다.

- 수정: 핸들러를 추가해 `FOR001-400`으로 응답한다. Spring 기본 동작과도 맞는다.

## 확인하지 못한 것

- **전시 이미지 업로드**: `FilePort`가 실제 S3를 호출하므로 로컬에서 돌리지 않았다.
  응답 모양 변경(`version` 추가)은 코드 수준 변경이고, 업로드 자체는 7단계 통합 QA에서 본다.
- **알림톡**: 이번 범위에 발송 경로가 없다.
- **동시 요청 경합**: 유니크 제약·`@Version`이 최종 방어선이라는 전제만 두고, 동시 호출은
  재현하지 않았다.
