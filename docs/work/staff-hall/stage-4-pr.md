## 본문

### 문제·결과

회장단이 모집 회차마다 열람자를 지정해, 지정된 운영진만 그 회차의 지원서를 볼 수 있게 한다. 3단계까지는 회장단만 지원서를 볼 수 있었고, 다른 운영진에게 보여 주려면 전역 ADMIN 권한에 기대야 했다.

- 회장단: 회차 학기 운영진 중에서 열람자를 고르고, 만료 시각을 정해 즉시 부여하고 언제든 회수한다.
- 열람자: 자신이 열람할 수 있는 회차를 찾아 그 회차의 지원서만 본다.
- 회수·만료 직후부터 그 사람의 다음 요청은 거절된다.

### 기존 코드 재사용

| 재사용 | 내용 |
| --- | --- |
| `ForifTeamRepository` | 회차 학기의 운영진 명단을 그대로 후보로 쓴다. |
| `StaffAccountRepository` | ADMIN 계정 보유 여부와 소속을 확인한다. 새 역할을 만들지 않았다. |
| `StaffAccountService.isPresidentTeam` | 회장단 통과 판정. |
| 3단계 `StaffApplicationRepository` | 이해충돌(같은 회차 지원자) 판정에 재사용. |

전역 role, JWT, SecurityConfig는 건드리지 않았다.

### 새로 추가한 부분

| 구분 | 내용 | 이유 |

| 도메인 | `StaffRecruitmentReviewer`, `StaffReviewerStatus` | 상태를 저장하지 않고 회수·만료 시각으로 계산한다. |

| ErrorCode 3개 | `FOR158`~`FOR160` | 계약에서 예약한 번호다. |

### 계약·권한

- 회장단 전용: `GET .../reviewer-candidates`, `GET .../reviewers`, `POST .../reviewers`, `DELETE .../reviewers/{userId}`
- ADMIN 공통: `GET /api/v1/admin/staff-recruitments/reviewable` — 회장단은 전체, 열람자는 유효 권한 회차만.
- 지원서 목록·상세는 **회장단 또는 해당 회차의 유효한 권한 보유자**로 넓혔다. 매 요청마다 DB에서 상태를 다시 확인한다.
- 부여 조건: 회차 학기 운영진 + ADMIN 계정 보유 + 같은 회차 지원자가 아닐 것. `expires_at`은 필수이며 미래여야 한다.
- 회수는 멱등이다. 권한이 없거나 이미 회수됐어도 204다.
- 재부여는 기존 행을 되살려 이력 행이 중복되지 않는다.
- 열람자는 모집 설정 변경·타인 초대를 할 수 없다. 해당 API는 회장단 검사를 그대로 쓴다.

### 이해충돌 정책

같은 회차 지원자에게는 권한을 부여할 수 없고(`FOR160`), 부여받은 뒤 지원하면 그때부터 열람이 막힌다(`FOR158`).

**회장단은 지원해도 차단하지 않았다.** 차단하면 모집 운영 자체가 막힐 수 있어 보류했다. 공정성 기준으로 회장단도 막아야 한다면 운영 정책을 확정한 뒤 반영하면 된다.

### 배포 영향

- migration `V7`은 신규 테이블 1개만 추가한다. 기존 테이블·행·API 응답은 변하지 않는다.
- 지원서 조회 권한이 넓어지지만 기본 상태에서는 권한 행이 없으므로 회장단만 열람 가능한 현재 동작과 같다.
- `SecurityConfig`와 JWT 발급 로직은 변경하지 않았다.
- Flyway는 자동 롤백되지 않는다. 되돌리려면 테이블을 제거하는 별도 migration이 필요하다.

### 남은 사항

- 실제 서버에서 초대 → 열람 → 회수/만료 → 403 흐름 확인이 남아 있다. (출시 차단, frontend와 공동)
- 회장단 이해충돌 정책 확정이 필요하다.
- `affiliation` 출처가 후보 목록(운영진 명단)과 열람자 목록(ADMIN 계정)에서 다르다. 통일할지 결정이 필요하다.
- 초대·회수 감사 이력은 권한 행의 `granted_by`·`revoked_by`·시각으로만 남는다. 별도 audit 테이블은 만들지 않았다.
