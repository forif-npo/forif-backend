# Git 작업 흐름

이 문서는 브랜치, 커밋, PR의 이름과 병합 경로를 정하는 기준입니다. 로컬 개발과 테스트는 [development.md](development.md), 배포 절차는 [deployment.md](deployment.md)를 참고합니다.

## 이슈와 브랜치

작업 이슈를 먼저 만들고 이슈 번호 하나로 브랜치 하나를 만듭니다. 이슈 번호가 없으면 설명만 붙인 임의의 브랜치를 만들지 말고 이슈를 먼저 발급받습니다. PR 번호는 이슈 번호를 대신하지 않습니다.

브랜치 이름은 **`<종류>/FOR-<이슈번호>`**로 통일합니다. 번호 뒤에 작업 설명을 덧붙이지 않습니다.

| 종류 | 사용 기준 | 예시 |
|---|---|---|
| `feature` | 새 기능·API | `feature/FOR-123` |
| `fix` | 기존 동작의 오류 수정 | `fix/FOR-123` |
| `docs` | 문서만 변경 | `docs/FOR-123` |
| `chore` | CI·빌드·의존성·설정 등 유지보수 | `chore/FOR-123` |
| `refactor` | 동작을 바꾸지 않는 코드 정리 | `refactor/FOR-123` |
| `test` | 제품 코드 변경 없는 테스트 보강 | `test/FOR-123` |

한 작업에 여러 종류가 섞이면 이슈의 주된 목적을 기준으로 종류를 고릅니다. 기능을 고치면서 테스트를 추가했다면 `fix`, 빌드 설정을 고치면서 문서를 함께 수정했다면 `chore`입니다.

새 브랜치는 최신 `dev`에서 만듭니다. 만들기 전에 원격에 같은 이름이 있는지 확인합니다.

```bash
git fetch origin
git ls-remote --heads origin 'feature/FOR-123'
git switch dev
git pull --ff-only origin dev
git switch -c feature/FOR-123
```

**`dev`, `release`, `main`에는 예외 없이 직접 푸시하지 않습니다.** 일반 푸시와 강제 푸시 모두 금지합니다. 변경 사항은 작업 브랜치에 푸시하고, 세 브랜치에는 PR 병합으로만 반영합니다. 긴급 수정과 문서 변경에도 같은 규칙을 적용합니다.

### 스택형 PR 금지

작업 브랜치를 다른 작업 브랜치에서 만들거나, 아직 `dev`에 병합되지 않은 다른 PR의 커밋을 병합·체리픽해 PR을 연쇄로 올리지 않습니다. 모든 작업 브랜치는 `dev`에서 만들고, 각 PR은 독립적으로 `dev`를 대상으로 올립니다.

다른 PR의 변경이 꼭 필요하다면 그 PR이 `dev`에 병합될 때까지 기다린 뒤, 최신 `dev`를 반영해 작업합니다. 여러 PR을 순서대로 병합해야만 현재 PR이 성립하는 상태로 올리지 않습니다.

## 커밋과 PR 제목

커밋과 PR 제목은 **`type(scope): 설명`** 형식을 씁니다. `type`은 소문자 영문이고, `scope`는 영향을 받는 영역을 짧게 적습니다. 영역이 여러 곳에 걸쳐 특정하기 어려우면 `scope`를 생략해 **`type: 설명`**으로 적을 수 있습니다. 설명은 변경 결과가 드러나는 한국어 문장으로 씁니다.

| 브랜치 종류 | 제목의 `type` | 제목 예시 |
|---|---|---|
| `feature` | `feat` | `feat(staff): 운영진 모집 회차 API 추가` |
| `fix` | `fix` | `fix(hall-of-fame): 이미지 업로드 검증 강화` |
| `docs` | `docs` | `docs(git): 브랜치와 PR 규칙 정리` |
| `chore` | `chore` | `chore(ci): Testcontainers 버전 업데이트` |
| `refactor` | `refactor` | `refactor(study): 조회 로직 정리` |
| `test` | `test` | `test(staff): 지원서 권한 테스트 보강` |

`Feature/for 123`, `운영진 모집 API 추가`처럼 자동 생성되거나 종류가 빠진 PR 제목을 그대로 두지 않습니다. 이슈 번호는 브랜치 이름과 PR 본문의 **관련 이슈**에 기록하고, 제목에는 변경 내용을 적습니다.

## PR과 병합

1. PR 대상 브랜치는 **`dev`**로 지정합니다. 저장소 기본 브랜치가 `main`이므로 생성할 때 대상을 확인합니다.
2. PR 본문에 관련 이슈, 변경 사항, 검증 결과, 리뷰어가 알아야 할 영향을 적습니다. 기능별 작업 기록은 PR 본문에 남깁니다. 공유 문서는 기존 파일을 수정하거나 목적이 드러나는 이름으로 추가하고, 이슈 번호만 붙인 작업 일지 Markdown 파일은 만들지 않습니다.
3. `./gradlew build`와 CI 결과를 확인합니다. 엔티티 변경에는 마이그레이션을 함께 확인하고, 새 마이그레이션은 [운영 데이터 복제본 리허설](database.md#리허설-방법)을 진행합니다.
4. 병합 전에 PR 대상과 변경 파일을 확인하고 최신 CI 결과를 확인합니다.
5. 병합한 작업 브랜치는 삭제하지 않습니다.

```bash
gh pr create --base dev --head feature/FOR-123 --title "feat(staff): 운영진 모집 회차 API 추가"
```

`dev` 이후 `release`와 `main`으로 반영하는 방법은 [배포 문서](deployment.md#브랜치와-릴리즈)를 따릅니다.
